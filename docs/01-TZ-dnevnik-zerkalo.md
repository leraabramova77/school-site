# ТЗ: современное зеркало НЕТ Школа (Next.js)

17 октября 2026

## 1. Цель проекта

Построить современный, красивый, адаптивный веб-дневник для школьников — зеркало существующей системы «Сетевой Город. Образование» (netschool.refal.kg). Новое приложение не имеет собственной базы данных и не получает доступа к серверу школы. Оно повторяет поведение официального мобильного приложения: авторизуется и запрашивает данные через публичный API старого сайта, а весь интерфейс рисует заново — красиво и удобно для телефона.

**Что должно получиться:**

- Ученик вводит те же логин и пароль, что и на старом сайте.

- Видит дневник, оценки, расписание и объявления в чистом современном интерфейсе, который отлично открывается на мобильном.

- Старый сайт выступает «бэкендом» (прокси к базе данных): наше приложение обращается к нему от имени пользователя и показывает полученные данные.

**Жёсткие принципы (нарушать нельзя):**

1.  **Никаких паролей нигде не хранить** — ни в базе, ни в логах, ни в localStorage. Пароль используется один раз для входа и сразу забывается.

2.  **Все запросы к старому сайту идут только с сервера** нашего приложения, никогда напрямую из браузера ученика.

3.  **Открытый исходный код** — чтобы одноклассники могли убедиться, что их данные в безопасности.

**Для кого:** школьники УВК «Рефал» и других школ в этой системе. Основной сценарий — быстро глянуть оценки и домашку с телефона.

## 2. Что за система на том конце и как с ней говорить

Сайт — это **«Сетевой Город. Образование» (NetSchool) от компании ИРТех, версия 5.0.28346**. Это важно: у этой версии есть современный REST API `/webapi/`, через который работает официальное мобильное приложение. Именно этот API мы используем.

**Технические факты, подтверждённые осмотром страницы входа:**

| Параметр            | Значение                                                                  |
|---------------------|---------------------------------------------------------------------------|
| Движок              | Сетевой Город. Образование (ИРТех), NetSchool                             |
| Версия              | 5.0.28346                                                                 |
| Бэкенд              | Классический ASP (`/asp/scripts/ajaxmethods_login.asp`) + REST `/webapi/` |
| Фронт старого сайта | jQuery 1.11, Bootstrap 3, Underscore                                      |
| Хеш пароля          | MD5 с солью, на клиенте (`md5r.min.js`)                                   |
| Цепочка входа       | Страна → регион → город → школа (ОО) → логин/пароль                       |

**Логин-флоу (повторяем мобильное приложение):**

1.  `GET /webapi/auth/getdata` → сервер отдаёт `lt`, `ver` и `salt` (соль).

2.  Хеш пароля считается на нашем сервере: `pw = md5(salt + md5(пароль в кодировке windows-1251))`, затем берётся нужная длина (как в `md5r`).

3.  `POST /webapi/login` с полями `loginType`, идентификаторами школы (`cid`, `sid`, `pid`, `cn`, `sft`, `scid`), `un` (логин), `pw`, `lt`, `ver`.

4.  В ответ приходит токен доступа `at` + `expires`. Дальше все запросы идут с заголовком `at: <токен>` (плюс обычно cookie-сессия ASP).

**Эндпоинты, которые понадобятся** (точные пути сверить с библиотекой `netschoolapi` и с реальными запросами в F12 → Network):

- Справочники для формы входа: `GET /webapi/prepareloginform` (страны/регионы/школы и их id).

- Данные ученика и год обучения: `GET /webapi/student/diary/init`, `GET /webapi/years/current`.

- Дневник с оценками и домашкой: `GET /webapi/student/diary?yearId=...&weekStart=...&weekEnd=...&studentId=...`.

- Объявления: `GET /webapi/announcements`.

- Итоговые/средние оценки, просроченные задания — аналогично под `/webapi/`.

- Выход: `POST /webapi/auth/logout` (чтобы корректно завершать сессию на старом сайте).

> Важно: версия в Киргизии может отличаться от российской (другие поля, возможна капча). Первый шаг разработки — войти в реальный аккаунт, открыть F12 → Network и записать реальные запросы/ответы `/webapi/` — это точная карта API для этой школы.

Библиотека-ориентир (Python, но удобно читать как справочник по эндпоинтам): [netschoolapi](https://pypi.org/project/netschoolapi/) и [её исходники](https://gitflic.ru/project/nm17/net-school-api).

## 3. Архитектура

Браузер ученика говорит только с нашим Next.js-сервером; только сервер говорит со старым сайтом. Напрямую из браузера к netschool.refal.kg ходить нельзя: это заблокирует CORS, и токен стал бы виден JavaScript-у страницы.

    [Телефон ученика]
          │  HTTPS, httpOnly-cookie с зашифрованной сессией
          ▼
    [Next.js на Vercel]
      ├─ страницы (React Server Components)
      └─ /api/* Route Handlers  ← единственное место, где есть токен в открытом виде
          │  HTTPS, заголовок at: <токен>
          ▼
    [netschool.refal.kg /webapi/]  →  база данных школы

**Стек:**

| Слой              | Выбор                                       | Зачем                                         |
|-------------------|---------------------------------------------|-----------------------------------------------|
| Фреймворк         | Next.js 15+ (App Router), TypeScript strict | Серверный код и UI в одном проекте            |
| Стили             | Tailwind CSS v4 + shadcn/ui (Radix)         | Быстро, красиво, доступно                     |
| Анимации          | Motion (Framer Motion)                      | Плавные переходы и жесты                      |
| Иконки            | lucide-react                                | Единый стиль                                  |
| Данные на клиенте | TanStack Query                              | Кэш, перезапросы, pull-to-refresh             |
| Валидация         | Zod                                         | Проверка входных данных и ответов старого API |
| Сессия            | iron-session или jose (JWE)                 | Зашифрованная cookie, без базы                |

| Хостинг           | Vercel                                      | Бесплатно, деплой из GitHub                   |

**Своей базы данных нет.** Мы ничего не храним о пользователях — сессия живёт только в зашифрованной cookie в браузере ученика. Меньше данных — меньше что может утечь.

**Риск с сетью.** Серверы Vercel находятся в США/Европе. Если школьный сервер блокирует зарубежные IP или отвечает очень медленно: (1) выбрать регион функций поближе (например `fra1` Франкфурт); (2) если не поможет — маленький прокси на дешёвом VPS в КР, доступный только нашему серверу по секретному ключу. Проверить это на Этапе 0.

## 4. Безопасность (главное требование)

Любая задача считается невыполненной, если нарушает хотя бы одно правило ниже. Мы обрабатываем чужие пароли и оценки несовершеннолетних, поэтому безопасность важнее скорости и фич.

### 4.1. Пароли

- Пароль живёт только в памяти одного запроса `POST /api/auth/login`: пришёл → захеширован с солью → отправлен на старый сайт → забыт.

- ЗАПРЕЩЕНО сохранять пароль (или его хеш) в cookie, localStorage, sessionStorage, IndexedDB, базу, кэш, файлы, логи, аналитику, Sentry.

- Форма логина отправляется только POST-ом в теле, никогда в URL или query-строке. Поле с `autocomplete="current-password"`, чтобы работал менеджер паролей телефона.

- Функция «Запомнить меня» = долгоживущая сессия, а НЕ сохранённый пароль. Когда токен старого сайта истёк — просим войти заново.

### 4.2. Сессия и токен

- Токен `at` и cookie старого сайта хранятся только в **зашифрованной** cookie (iron-session или JWE через `jose`, AES-256-GCM).

- Флаги cookie: `HttpOnly`, `Secure`, `SameSite=Lax` (или `Strict`), `Path=/`, имя с префиксом `__Host-`. Срок жизни не дольше, чем живёт токен старого сайта.

- JavaScript в браузере **никогда** не видит токен. Клиент получает только готовые данные (оценки, уроки), очищенные от служебных полей.

- Выход (`/api/auth/logout`): вызвать logout на старом сайте + удалить cookie + очистить кэш TanStack Query.

- При ответе 401 от старого сайта — удалить cookie и отправить на экран входа.

### 4.3. Секреты и ключи

- Единственный секрет проекта — `SESSION_SECRET` (минимум 32 случайных байта, сгенерировать `openssl rand -base64 32`). Если будет прокси в КР — ещё `PROXY_SECRET`.

- Секреты хранятся ТОЛЬКО в Environment Variables на Vercel (и в локальном `.env.local`).

- Переменные с префиксом `NEXT_PUBLIC_` попадают в браузер. **Никогда не класть туда секреты.** Линтер-правило или проверка в CI должна падать, если слова SECRET/KEY/TOKEN встречаются в `NEXT_PUBLIC_*`.

- Файл `src/server/env.ts` валидирует переменные через Zod при старте и начинается с `import 'server-only'`, чтобы сборка упала, если его случайно импортируют в клиентский компонент.

- Все файлы в `src/server/` — с `import 'server-only'`.

### 4.4. Защита от утечек в Git

- `.gitignore` с самого первого коммита: `.env*` (кроме `.env.example`), `.vercel`, `*.har`, `*.log`, папка с записанными ответами API.

- `.env.example` с именами переменных и пустыми значениями.

- Pre-commit хук (husky + **gitleaks**), который блокирует коммит с секретами. Тот же gitleaks — в GitHub Actions.

- Включить GitHub Secret Scanning и Push Protection в настройках репозитория.

- **Тестовые фикстуры** (примеры ответов API) — только с придуманными данными. Никаких настоящих ФИО, оценок, токенов из F12.

- Если секрет всё-таки попал в Git — не просто удалить файл, а сразу **сменить секрет** (история Git помнит всё).

### 4.5. Логи и ошибки

- Запрещено логировать тела запросов и ответов, заголовки `cookie`, `at`, `authorization`, `set-cookie`.

- Сделать свой логгер с белым списком полей (метод, путь без query, статус, длительность). `console.log` в `src/server` запрещён правилом ESLint.

- Пользователю ошибки показываются общими словами («Неверный логин или пароль», «Сайт школы не отвечает»), без stack trace и сырых ответов старого сайта.

- Аналитика — только Vercel Analytics без cookie, без персональных данных. Никаких сторонних трекеров.

### 4.6. Защита API и страниц

- **SSRF**: базовый URL старого сайта зашит константой в коде (`https://netschool.refal.kg`). Сервер никогда не ходит по URL, пришедшему от клиента. Никакого универсального «прокси на любой путь» — только явные маршруты для нужных эндпоинтов.

- Все входные параметры (даты недели, id) валидируются Zod. Ответы старого сайта тоже валидируются — лишние поля отбрасываются.

- **XSS**: текст объявлений и домашки может содержать HTML. Рендерить только через санитайзер (DOMPurify / `sanitize-html` с белым списком тегов). `dangerouslySetInnerHTML` без санитайзера запрещён.

- **CSRF**: состояние меняют только POST-запросы; проверять заголовок `Origin` на совпадение с нашим доменом + `SameSite` cookie.

- **Rate limiting** на `/api/auth/login`: не больше 5 попыток за 10 минут с одного IP (Upstash Ratelimit или Vercel Firewall). Иначе наш сайт станет инструментом перебора паролей, а старый сайт заблокирует IP Vercel.

- Кэширование: все ответы с личными данными — `Cache-Control: private, no-store`. Никакого ISR/статического кэша на страницах с данными — иначе один ученик может увидеть оценки другого.

- Service worker PWA не кэширует `/api/*`; при выходе чистит все кэши.

- Заголовки безопасности в `next.config`: Content-Security-Policy (с nonce), `Strict-Transport-Security`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy`, `frame-ancestors 'none'`.

### 4.7. Зависимости и проверки

- Только известные пакеты; `pnpm-lock.yaml` в репозитории; Dependabot включён; `pnpm audit` в CI.

- Перед каждым релизом — чеклист из раздела 7 и проверка бандла: поиск по `.next/static` на строки `SESSION_SECRET`, `netschool.refal.kg/webapi` и похожие должен быть пустым.

## 5. Дизайн (главное требование)

Цель — чтобы дневник ощущался как хорошее нативное приложение уровня Apple/Linear/Arc, а не как сайт. Проверка: человек открывает с телефона и не догадывается, что это веб.

### 5.1. Принципы

- **Mobile-first.** Всё рисуется сначала под экран 375–430 px, потом расширяется на планшет и десктоп. Запрещён горизонтальный скролл страницы.

- **Спокойно, чисто, с характером.** Много воздуха, один акцентный цвет, цвет несёт смысл (оценки), а не украшает. Никаких шаблонных фиолетовых градиентов и теней на всём.

- **Главное — за 1 секунду.** Первый экран после входа отвечает: какие уроки сегодня/завтра, что задано, какие новые оценки.

- **Доступность**: контраст текста не ниже WCAG AA (4.5:1), зоны нажатия не меньше 44×44 px, видимый focus, поддержка `prefers-reduced-motion`, цвет никогда не единственный носитель смысла (оценка всегда подписана цифрой).

### 5.2. Дизайн-токены

- **Цвета** — CSS-переменные в OKLCH для светлой и тёмной темы: `--bg`, `--surface`, `--surface-2`, `--border`, `--text`, `--text-muted`, `--accent`. Семантика оценок: 5 — зелёный, 4 — сине-зелёный, 3 — янтарный, 2 — красный, долг/пропуск — приглушённый красный. Мягкие фоны (`*-soft`) для чипов.

- **Шрифты**: Inter или Geist для текста (с кириллицей), цифры — `font-variant-numeric: tabular-nums`. Шкала: 13 / 15 / 17 / 20 / 28 / 34 px. Подключение через `next/font` (без запросов к Google из браузера).

- **Скругления**: карточки 16–20 px, чипы — полные. **Отступы** — шкала 4/8/12/16/24/32. Боковой отступ на мобилке 16 px.

- **Тёмная тема** обязательна: по умолчанию по системе + переключатель в профиле (next-themes). Тёмная — не чисто чёрная, а глубокий графит.

- `theme-color` и safe-area (`env(safe-area-inset-*)`) для чёлки iPhone и нижней полоски.

### 5.3. Навигация

- **Мобилка**: нижний tab bar из 4 пунктов — «Сегодня», «Дневник», «Оценки», «Ещё» (объявления, профиль, тема, выход). С лёгким блюром подложки.

- **Десктоп** (≥ 1024 px): боковая панель слева, контент в центре с макс. шириной, на «Дневнике» — неделя целиком сеткой.

### 5.4. Экраны

|---------------|---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|

### 5.5. Состояния и анимации

- **Загрузка** — скелетоны в форме настоящих карточек, не спиннеры. **Пусто** (выходной, каникулы) — дружелюбная иллюстрация и текст. **Ошибка** — понятное сообщение и кнопка «Повторить». **Офлайн** — баннер.

- Анимации короткие (150–250 мс), пружинные: появление карточек, смена дня свайпом, раскрытие домашки, нажатие (scale 0.98). При `prefers-reduced-motion` — без движения.

- Pull-to-refresh на мобилке. Оптимистичное отображение кэша со свежим обновлением.

### 5.6. Качество (критерии приёмки)

- Lighthouse (мобильный): Performance ≥ 90, Accessibility ≥ 95, Best Practices ≥ 95.

- Проверено на ширинах 360, 390, 430, 768, 1280 px и в обеих темах. Работает в Safari iOS и Chrome Android.

- Перед вёрсткой агент делает одну страницу `/design` со всеми токенами и компонентами на придуманных данных — сначала утверждаем вид, потом подключаем данные.

## 6. Этапы и задачи

Агент выполняет этапы строго по порядку. Каждая задача — отдельный небольшой коммит. Этап закрыт, когда пройдены `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm build` и чеклист безопасности этапа.

### Этап 0. Разведка API (делает автор проекта вручную)

- Войти в свой аккаунт на netschool.refal.kg с компьютера, F12 → Network, фильтр `webapi`.

- Записать точные пути, методы, поля и формат ответов: вход, дневник, оценки, объявления, выход.

- Составить файл `docs/api-map.md` — только структура, все реальные значения (ФИО, оценки, токены, cookie) заменить на выдуманные. HAR-файлы в репозиторий не класть.

- Проверить: есть ли капча при входе, сколько живёт токен, отвечает ли сервер из-за рубежа (через тестовую функцию на Vercel).

### Этап 1. Каркас и защита репозитория

- `create-next-app` с TypeScript (strict), App Router, Tailwind, ESLint, `src/`, pnpm.

- `.gitignore` (см. 4.4) и `.env.example` — **до первого коммита**.

- husky + lint-staged + gitleaks в pre-commit.

- GitHub Actions: lint, typecheck, test, build, gitleaks, `pnpm audit`.

### Этап 3. Серверный клиент к старому API

- `src/server/env.ts` — Zod-валидация переменных, `server-only`.

- `src/server/netschool/client.ts`: базовый URL-константа, таймаут 10 с, один повтор при сетевой ошибке, нормализация ошибок (401 / 5xx / таймаут).

- Функция хеширования пароля (соль + MD5, windows-1251 через `iconv-lite`) + юнит-тесты на выдуманных значениях.

- Методы: `getLoginForm`, `login`, `logout`, `getDiary(week)`, `getAnnouncements`, `getGrades`.

- Zod-схемы всех ответов и мапперы в чистые типы (`Lesson`, `Grade`, `Announcement`) — без служебных полей.

- Безопасный логгер с белым списком полей + тест, что токен и пароль в лог не попадают.

### Этап 4. Авторизация и сессия

- `src/server/session.ts`: зашифрованная cookie `__Host-session` (HttpOnly, Secure, SameSite=Lax).

- `POST /api/auth/login`: валидация, rate limit, проверка Origin, вход на старом сайте, запись сессии. Ответ клиенту — только `{ ok, name }`.

- `POST /api/auth/logout`: выход на старом сайте + удаление cookie.

- Middleware: без сессии → редирект на `/login`; с сессией на `/login` → `/today`.

- Экран входа в два шага (школа → логин/пароль) с ошибками и состоянием загрузки.

- Тесты: в ответах API нет токена; cookie имеет все флаги; 6-я попытка входа получает 429.

## 7. Деплой на Vercel

Репозиторий на GitHub подключается к Vercel; каждый push в `main` — продакшен, каждый PR — preview.

1.  Импортировать репозиторий в Vercel.

2.  Settings → Environment Variables: `SESSION_SECRET` (отдельный для Production и Preview), при необходимости ключи Upstash и `PROXY_SECRET`. Отметить как **Sensitive**.

3.  Settings → Functions: регион поближе к КР (например `fra1`), если на Этапе 0 сервер школы отвечал медленно.

4.  Preview-деплои закрыть Vercel Authentication (чтобы случайные люди не вводили пароли на тестовых версиях).

5.  Включить Vercel Firewall / Attack Challenge Mode для `/api/auth/login`.

6.  По желанию — свой домен. Название и домен **не должны выдавать себя за официальный сайт** школы или ИРТех (без их логотипов и похожих адресов) — иначе сайт будет выглядеть как фишинг. Придумать своё имя и логотип.

**Чеклист перед запуском:**

- В DevTools → Application → Cookies есть только `__Host-session` с HttpOnly/Secure; в localStorage нет ничего секретного.

- В DevTools → Network нет ни одного запроса из браузера на netschool.refal.kg; ответы `/api/*` не содержат токена.

- Поиск по собранным JS-файлам не находит секретов.

- Vercel → Logs: нет паролей, токенов, ФИО, оценок.

- gitleaks по всей истории репозитория — чисто.

- securityheaders.com — A; Lighthouse — как в 5.6.

- Выход действительно разлогинивает: кнопка «назад» не показывает оценки.

- Два разных аккаунта в двух браузерах никогда не видят данные друг друга (проверка кэша).

## 8. Риски и рекомендации

| Риск                                                      | Что делать                                                                                                                              |
|-----------------------------------------------------------|-----------------------------------------------------------------------------------------------------------------------------------------|
| Ученики доверяют нам свои пароли                          | Раздел 4 + открытый код + честная страница «О безопасности». Никаких данных на нашей стороне.                                           |
| Старый сайт блокирует IP Vercel или неофициальные клиенты | Бережная нагрузка: кэш на клиенте, никаких фоновых опросов, rate limit. Запасной план — прокси в КР.                                    |
| ИРТех обновит API                                         | Все ответы через Zod; при несовпадении — понятная ошибка, а не белый экран.                                                             |
| Капча или другой вход в киргизской версии                 | Выяснить на Этапе 0. Капчу не обходить — если она есть, показывать её пользователю или пересмотреть план.                               |
| Сайт примут за фишинг                                     | Своё имя и дизайн, без логотипов ИРТех/школы, чёткая подпись «неофициальный клиент».                                                    |
| Правила использования системы                             | Прочитать условия использования; до широкого запуска показать проект администрации школы или администратору Сетевого Города в «Рефале». |

**Главная рекомендация:** сначала сделать работающую версию только для себя, потом показать её школе. С их одобрением проект не заблокируют, а ещё это отличное портфолио.
